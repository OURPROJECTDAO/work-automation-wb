# 워크플로우: 쿠팡 로켓그로스 정산 (coupang-rocketgrowth-settlement)

> 이 워크플로우를 건드리기 전 이 파일을 읽는다. 전역 함정은 pitfalls.md.

## 요약
- 쿠팡 로켓그로스(RG)는 쿠팡 자체 창고에서 직접 배송 — 우리 쪽 발주(포장·배송)가 없어서
  **cheonnyeon-upload 파이프라인(발주자료 기반)에 안 잡힘**. 매달 별도 보충 입력 필요.
- **매달 반복.** 5월=사용자 수작업 / 6월=첫 자동화(2026-07-02) / 7월=반출·재고대사까지 확장(2026-08-03).
- 산출 = 천년경영 "쿠팡전체" 시트와 동일 컬럼 구조의 별도 xlsx → 사용자가 천년경영에 수기 입력.

## ★ 0. 로켓창고 = 위탁재고 계정 (2026-08-03 규명, 이 워크플로우의 뼈대)
ERP 거래처 `쿠팡(로켓창고)`는 **매출처가 아니라 위탁재고 계정**이다.

1. 로켓창고로 물건을 보낼 때 → 전량 **매출(출고) 전표 (+)**
2. 실제 판매되면 → 판매통계 기반으로 **쿠팡 채널 매출을 별도 입력**
3. 그대로 두면 이중계상 → **판매된 수량만큼 로켓창고 전표를 음수 차감 (−)**

사용자 표현: **"창고에서 빠지고 매출처에 더해진다."**
반출·유실도 같은 방식으로 음수 상계. 따라서 **로켓창고 잔액 = 아직 쿠팡 창고에 남아있는 실재고 금액**이어야 한다.

- 차감 일자 = 그 달 발주일과 동일하게 일괄(5/31·6/28·7/26 실적).
- 검증 근거: 6/28 음수 28건 중 27건이 6월 판매수량과 정확히 일치.
- ⚠️ **회송 상계**: 회송(쿠팡이 안 받고 돌려보냄)은 입고 전표를 고치는 대신 **같은 날 음수 행으로 상계**하기도 함
  (65-54 6/23 +240×2/−240×2, 265-12-30-01 6/19 +252/−252). → **입고량 집계는 반드시 순액(양수+음수)으로.**
  양수만 더하면 회송분이 입고로 잡혀 유실이 부풀려진다.

## ★ 1. 매달 실행 체크리스트 (판매분)
1. 쿠팡 WING **판매통계 export**(해당 월 1일~말일, 시트명 '판매통계') 요청.
2. **TOTAL행 제외**하고 파싱(마지막 행 A열='TOTAL'). 안 하면 정확히 2배. 항상 이 필터부터.
   ★같은 함정이 **반출목록·입고목록에도 있음**(합계행·일자별 소계). 어떤 쿠팡 export든 하단 합계행 먼저 확인.
3. 관리코드 매핑: **`work-automation-data:market/coupang_rg/option_map.csv`** 를 1순위로 사용(2026-08 박제).
   - 없는 옵션ID만 신규 확인 → 확인되면 option_map.csv에 append.
   - 신규 확인은 옵션명 텍스트로 product_master 재검색(브랜드+규격) → **내재단가 검산**으로 확정.
   - 매출 0인 미매칭은 무시(다음에 팔리면 그때 확인). ★단, "다음에 확인" 건은 실제로 다음 달 팔림 — 6월 3건 전부 7월 회수.
4. **수량매칭**: 옵션명의 "n개" 패턴. 옵션명에 박스개수가 명시돼 있으면 그 값을 그대로 사용
   (product_master 박스내품과 다시 곱하면 이중계산).
   ★교차검증: 옵션명 n이 **ERP 규격의 배수와 일치**하는지 확인(140g*48 ↔ "48개"). 7월 전건 일치.
5. **검산(필수)**: 관리코드별 내재단가(순매출÷실제수량) vs product_master 낱개 매출단가.
   같은 코드 여러 옵션이면 내재단가끼리 비교(대량구매 할인 감안 단조감소여야 정상).
   최종적으로 관리코드별 순매출 합계 = 원본 TOTAL 제외 합계 **정확 일치** 확인.
6. 수수료율 = **11.66%** 고정(일반 쿠팡 12%와 다름).
7. 산출 [쿠팡전체] 시트:
   - A 일자 = 그 달 발주일 일괄(사용자 지정. 6월 2026-06-28 / 7월 2026-07-26)
   - B 관리코드 · C 상품명(ERP) · D 주문수량(=실제수량, 매출 0 코드는 행 제외)
   - E 평균단가 `=F/D` · F 정산금액 = 순매출 gross · G 선결제택배비 = **0**
   - H 실제기입단가 `=F*(1-0.1166)/D` (F에 차감 넣지 말 것)
8. **판매분 음수 차감 시트도 같이 생성**(§0의 3번). 일자는 판매분과 동일. 단가는 ERP 로켓 입고 전표의 자동생성 판매단가.

## 2. 반출(회수) 발생 시
- 반출목록(WING) = 반출 상품목록 + 상차된 상품목록. **여러 화면으로 나뉘므로 합계 대조 필수.**
- SKU 단위 수량 → **수량매칭 곱해 낱개로 환산**.
- 단가 = ERP 로켓 입고 전표의 판매단가. **수수료 미적용**(매출이 아니라 재고 반환).
- 일자 = 실제 반출일(7/30·7/31처럼 일자별로 나눠 기입).
- 부호 = 음수.

## 3. 입고 전표 대조 (재고 정합 깨졌을 때)
**규칙: ERP 입고수량 = WING "판매개시" 수량.**
입고생성·입고중·미배송·회송확정은 전부 제외. (입고중 = 신청했는데 실제로 안 들어간 것 → 반영하면 안 됨)

- WING > 로켓그로스 > 입고관리에서 건별 화면을 받아 ERP와 1:1 대조.
- 평소엔 규칙대로 잘 기입되고 있음(2026-05~07 11건 중 오류 8건, 나머지 전건 일치).
- 같은 날 같은 코드가 여러 줄로 분할 기입되는 건 **정상**(파렛트 단위). 합계로 비교할 것.
  ★2026-08-03에 이걸 "중복 입력"으로 오판했다가 실입고와 대조해서 정상 확인함.

## 4. 4축 재고 대사 (반기/이벤트 시)
**입고 = 판매 + 반출 + 실재고 + 유실**

| 축 | 원천 |
|---|---|
| 입고 | ERP 로켓창고 전표 **순액**(정산일 제외) |
| 판매 | 쿠팡 판매통계 전 기간 × 수량매칭 |
| 반출 | 반출목록 → 낱개 환산 |
| 실재고 | WING 재고화면(판매가능) |
| 유실 | **나머지 잔여** — 규명이 아니라 잔여값 |

- 유실은 세 축을 다 맞춘 뒤 설명 안 되는 부분. **어느 한 축이라도 놓치면 그만큼 유실로 밀려든다.**
  → 유실 확정 전에 입고 전수 대조를 반드시 먼저 할 것(2026-08-03: 갭 304 → 입고 오류 8건 제거 후 200).
- 유실률 1~3%는 물류센터 취급 감모로 자연스러운 범위. 특정 코드만 크게 튀면 입고/회송 오류를 의심.
- ⚠️ **쿠팡 창고 파손·분실은 원래 보상 대상** — 보상 내역 확인 후 해당분은 유실에서 제외.
- 부호가 반대로 짝을 이루는 두 코드(A +n / B −n)가 **동일 브랜드·동일 규격·동일 단가**면 창고 내 혼입 →
  **상계 처리(양쪽 유실 0)**. 음수 유실 전표를 만들지 않는 게 깔끔함.

## 재사용 자산
- **`work-automation-data:market/coupang_rg/option_map.csv`** — 옵션ID→관리코드·수량매칭 정본(2026-08-03 박제).
  6월 매핑 + 7월 신규 확정 + 반출·입고 대조로 확인된 코드 전부 포함.
- product_master는 `work-automation-app/reference/product_master.csv`에서 매번 최신본 읽을 것.

## 계산식
- 실제수량 = 순 판매 상품 수 × 수량매칭
- 정산금액(F) = 순매출 gross
- 실제기입단가(H) = F × (1 − 0.1166) ÷ 실제수량
- 택배비(G) = 0
