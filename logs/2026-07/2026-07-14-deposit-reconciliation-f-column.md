# 입금 대사 (은행 입금내역 ↔ 천년경영 ERP 입금전표) — 신규 워크플로우 v1

## 무엇 / 왜
사업 입금 계좌(오픈마켓 정산 수취계좌 398-075486-01-018)에 실제로 들어온 입금을,
천년경영 ERP에 수기로 등록한 입금전표와 대사(reconcile)하는 업무.
목적 = 총액이 아니라 **거래처(채널) 오분류 탐지**. 은행 입금내역을 보고 사람이 ERP에
"어느 거래처 정산인지"를 수기 지정하므로, 총액은 항상 맞지만(같은 소스) 개별 건이
잘못된 거래처로 들어갈 수 있음.

기존에는 매크로 파일(입금-천년경영_비교_v1.xlsm)로 M열(예금주명) 기준 대사를 했으나,
M��은 PG사 법인명이라 한 PG가 여러 채널에 걸치면 구분 불가 → 오분류를 못 잡음.
이번에 F열(거래내용) 기준 + "다수결" 원칙으로 방법론을 개선.

## 입력 파일 (2건, 기간 2026-01~06)
1. 은행: `거래내역조회_입출식_예금1-6월.xlsx` (헤더 3행째)
   - B=거래일시(datetime), D=입금, **F=거래내용**(수기 입력·거래처 식별력 좋음),
     M=상대계좌예금주명(PG 법인명·식별력 약함)
   - 입금건 1,544건(1~6월), 합계 2,767,300,639원
2. ERP: `Exp260710_...입금전표관리__1-6월_.xlsx` (Sheet1)
   - 거래일자·거래처명·거래처명(약칭)·**결제금액**·결제방법(전건 '통장')·자료등록일시 등
   - 데이터 1,537건, 합계 2,765,458,808원

## 방법론 (확정)
1. **ERP 합계행 제거**: 파일 마지막 행이 거래처명 등 전부 빈칸 + 결제금액만 채운 TOTAL 행.
   제거 안 하면 ERP 총액이 은행의 정확히 2배로 잡혀 완전히 어긋나 보임(pitfalls TOTAL행 함정).
2. **거래 단위 매칭**: 은행 입금 각 건을 (거래일자, 금액) 완전일치로 ERP 등록건과 짝지음(±2~3일 허용).
   1,544건 중 1,535건 매칭(±0일 대부분). 이름 매핑이 아니라 개별 거래 매칭이라
   한 PG가 여러 채널로 갈려도 정확히 추적됨.
3. **F열 기준 + 다수결**: 각 F열(거래내용) 값이 ERP에서 어느 거래처로 갔는지 집계 →
   **압도적 다수 = 진짜 거래처, 소수로 튄 것 = 오분류 의심**. (사용자 확정 원칙:
   "절대 다수가 있는 쪽이 맞는 거래처, 한두 개 실수가 정황상 맞다")

## F열 → 천년경영 거래처 매핑 (2026 1~6월 확인분)
- 스마트스토어정 → 오픈마켓- 스마트스토어
- 지마켓 / 주식회사지마켓 / 옥션 → 오픈마켓(ESM/옥션.지마켓.G9)  ★더즌(M열)도 F열은 이쪽
- **주식회사마켓 / 주식회사마켓보로 → 오픈마켓- (주) 마켓보로** (사용자 확정)
- 쿠팡페이주식회 → 오픈마켓 쿠팡 (윙배송)
- 한국신용데이터 → 오픈마켓 (주) 한국신용데이터 (캐시노트)
- 알리익스프레스 / tosspaymen → 오픈마켓- 알리
- 제이티유통 → 제이티유통
- 우아한형제들 → 오픈마켓- (주) 우아한형제들 (배민상회)
- 리테일앤인사이트 → 주식회사 리테일앤인사이트
- 올웨이즈202601~06 → 오픈마켓- 올웨이즈
- (나머지 개인/B2B 소액은 F열 그대로 = 거래처명)

★ 사용자 확정 규칙: **(주)더즌은 ESM으로만 들어온다.** M열로는 더즌이 ESM+마켓보로로
  섞여 보이지만, F열(주식회사지마켓/옥션)로는 전부 ESM. 마켓보로는 은행에 별도 이름으로
  안 찍힘(F=주식회사마켓/마켓보로만) → 더즌 입금이 마켓보로일 수 없음.
